# Analytics Engineer — Developer Guidelines & Responsibilities

## 1. Role Overview
The Analytics Engineer is responsible for designing, implementing, and maintaining the analytics data models, metrics definitions, and event tracking for the Adaptive Examination & AI Learning Platform. This role bridges the gap between raw data generated by the platform (student actions, exam submissions, AI interactions) and actionable insights, ensuring data quality and availability.

## 2. Core Responsibilities
1. Define and maintain the platform's core metrics (student mastery, exam performance, AI usage, subscription conversion).
2. Design and implement analytics data models and pipelines.
3. Establish and manage the event tracking schema for all user actions.
4. Ensure data quality, consistency, and reliability across the data warehouse.
5. Create and maintain dashboards and reports for internal stakeholders.
6. Collaborate with engineering teams to ensure tracking is implemented correctly.
7. Manage data governance and access control for analytics data.

## 4. Phase-by-Phase Goals

### Phase 1 — Foundation
- Define event tracking for Authentication System (registration, login) and User Management CRUD (features 1.6, 1.7).
- Model data schemas based on the Database Package and Audit Logging outputs (features 1.2, 1.9).
- See docs/phases/phase-01-foundation.md for full details.

### Phase 2 — Academic Structure
- Define event tracking for Course Management and Student Course Enrollment (features 2.1, 2.6).
- Model academic hierarchy dimensions (Syllabus Tree) in the data warehouse.

### Phase 3 — Question Bank
- Define metrics for Question Bank Analytics (feature 3.8) and Question Tags (feature 3.4).
- Track question lifecycle status changes (DRAFT → PUBLISHED).

### Phase 4 — Exam Pattern
- Track Exam Pattern creation, versioning, and section rules configuration (features 4.1, 4.3).

### Phase 5 — Exam Generator
- Define metrics around Exam Generation Engine usage and manual vs. auto-generated exams (features 5.1, 5.4).

### Phase 6 — Exam System
- Define core exam performance metrics (score, time spent).
- Implement tracking for Student Exam Access, Exam Attempt Session, Answer Submission, and Exam Completion (features 6.1, 6.2, 6.3, 6.4).

### Phase 7 — Exam Archive
- Track historical access to the Exam Archive (feature 7.4).
- Ensure published exam snapshot metrics correctly relate back to original exams.

### Phase 8 — Student Analytics
- Build the foundation for student-facing analytics data models based on the Mastery Engine (@repo/mastery-engine) (feature 8.1).
- Define metrics and data tracking for Strengths Identification, Weakness Identification, and Syllabus Proficiency Map (features 8.2, 8.3, 8.4).

### Phase 9 — Personalized Practice
- Track Personalized Practice Paper Generation and Practice Attempt Tracking (features 9.2, 9.4).
- Define metrics for Adaptive Mastery Confirmation (feature 9.3).

### Phase 10 — Preview System
- Ensure all event tracking models correctly handle and filter out Preview Student Profiles and Impersonation activities (features 10.1, 10.3) utilizing the Preview Audit Trail (feature 10.5).

### Phase 11 — AI Question System
- Define AI Usage Tracking (feature 11.5), tracking AI requests per user, cost per provider, and utilization across Cloud AI Integration vs Local AI Model Support (features 11.7, 11.8).

### Phase 12 — AI Interview
- Track metrics around Controlled Natural Conversation Engine interactions, STT/TTS latencies, and Interview Assessment Engine scores (features 12.3, 12.4, 12.5, 12.6).

### Phase 13 — Subscriptions
- Implement full funnel tracking for Subscription Management and AI Credit System (features 13.2, 13.3).
- Define usage and entitlement limit metrics utilizing the Entitlement Engine (feature 13.1, 13.4).

### Phase 14 — Production Hardening
- Refine Audit System Enhancement (feature 14.2) models for comprehensive reporting.
- Finalize production dashboards for launch monitoring.

## 5. Key Guidelines
### 5.1 Technical Standards
- Event names must follow a standard `Noun Action` convention (e.g., `Exam Started`, `Question Answered`).
- All data models must be documented in a central data dictionary.
- SQL queries must be optimized and follow project coding standards.

### 5.2 Collaboration Model
- Work closely with Backend Engineers to ensure API events are triggered.
- Consult with Product Managers to align metrics with business goals.

### 5.3 Tools & Processes
- Data Warehouse: PostgreSQL (analytics replica or dedicated DWH).
- Tracking: Segment/PostHog (or similar defined tool).
- Modeling: dbt (Data Build Tool) or similar SQL-based transformation tool.

## 6. Do's ✅
1. Do document every single metric definition clearly.
2. Do validate event tracking payloads with developers before deployment.
3. Do design data models to be scalable and performant.
4. Do monitor data quality continuously.
5. Do communicate data discrepancies proactively.
6. Do use standard naming conventions for all events and properties.
7. Do prioritize tracking user value moments (e.g., viewing an exam report).
8. Do collaborate on data privacy and compliance.
9. Do version control all analytics code (SQL, dbt models).
10. Do create clear, actionable dashboards.
11. Do test data pipelines under simulated load.
12. Do define explicit timezones for all time-based metrics.
13. Do audit existing tracking periodically.
14. Do map events to specific product features.
15. Do ensure metrics are easily calculable from raw data.

## 7. Don'ts ❌
1. Don't create ambiguous event names.
2. Don't change metric definitions without communicating to stakeholders.
3. Don't write complex, unoptimized SQL queries.
4. Don't ignore data privacy regulations (PII in tracking).
5. Don't assume developers know what to track without a spec.
6. Don't build dashboards without a clear use case.
7. Don't rely on manual data extraction.
8. Don't track unnecessary data that inflates storage costs.
9. Don't mix different timezones in reporting.
10. Don't let broken tracking remain unaddressed.
11. Don't use different definitions for the same metric in different places.
12. Don't bypass the data dictionary.
13. Don't hardcode IDs in analytics queries.
14. Don't ignore edge cases in data transformations.
15. Don't deploy models without testing them against staging data.

## 8. Quality Gates
- Tracking Schema Review: All new events must be reviewed before implementation.
- Data Model PRs: SQL/dbt code must be reviewed by another engineer.
- Data Validation: New metrics must match expected baselines before release.

## 9. Escalation Path
- Missing Data: Escalate to Backend/Frontend leads.
- Data Quality Issues: Escalate to Data Engineering/Infrastructure.
- Metric Definition Conflicts: Escalate to Product Management.

## 10. KPIs & Success Metrics
- Data Pipeline Uptime (99.9%).
- Tracking Accuracy (percentage of correctly fired events).
- Dashboard Adoption Rate by stakeholders.
- Time to resolve data discrepancies.
