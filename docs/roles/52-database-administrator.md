<Database Administrator (DBA) — Developer Guidelines & Responsibilities>
## 1. Role Overview
The Database Administrator (DBA) is responsible for the operational health, performance, and reliability of the PostgreSQL 16 databases powering the Adaptive Examination Platform. You own database tuning, connection pooling (PgBouncer), backup strategies, query performance monitoring, and the safe execution of migrations in staging and production environments.

## 2. Core Responsibilities
1. Manage PostgreSQL 16 server configuration, performance tuning, and scaling.
2. Implement and manage connection pooling using PgBouncer.
3. Design, implement, and test backup and disaster recovery strategies for exam data.
4. Monitor query performance, identify slow queries, and recommend indexing strategies.
5. Execute database migrations (generated by Prisma) safely in production environments.
6. Manage database user access, roles, and security policies.
7. Ensure high availability (HA) and setup replication for read-heavy workloads.
8. Monitor database storage, CPU, and memory utilization.

### Phase 4 — Exam Pattern

- Definition of done: Complex join queries perform within SLA.

### Phase 5 — Exam Generator

### Phase 6 — Exam System

### Phase 7 — Exam Archive

- Definition of done: Storage growth is monitored and managed efficiently.

### Phase 8 — Student Analytics

## 5. Key Guidelines
### 5.1 Technical Standards
- PostgreSQL 16 must be configured for optimal memory usage (shared_buffers, work_mem).
- All applications must connect via PgBouncer in transaction pooling mode.
- Backups must be tested via restoration at least monthly.
### 5.2 Collaboration Model
- Work closely with Database Engineers to review Prisma migrations before execution.
- Work with DevOps for database monitoring and alerting setup.
### 5.3 Tools & Processes
- PgBouncer, pgAdmin / psql.
- Monitoring tools (e.g., Datadog, Prometheus/Grafana, pg_stat_statements).
- Prisma (for migration execution and review).

## 6. Do's ✅
1. Do use PgBouncer in transaction mode for Prisma connections.
2. Do enable and monitor `pg_stat_statements` to identify slow queries.
3. Do enforce strict role-based access control within the database.
4. Do test backup restoration processes regularly.
5. Do configure Point-in-Time Recovery (PITR) for critical databases.
6. Do use read replicas for heavy reporting and analytics queries.
7. Do review all Prisma migrations before applying them to production.
8. Do monitor database connection counts and pool utilization.
9. Do tune `work_mem` based on expected query complexity.
10. Do set statement timeouts to prevent rogue queries from locking resources.
11. Do monitor disk I/O and storage capacity proactively.
12. Do apply database security patches during maintenance windows.
13. Do use connection limits on roles to prevent resource exhaustion.
14. Do document all manual database interventions or configuration changes.
15. Do set up alerts for high CPU, memory, and slow query spikes.

## 7. Don'ts ❌
1. Don't allow applications to connect directly to PostgreSQL bypassing the pooler.
2. Don't run long-running migrations (e.g., creating indexes without `CONCURRENTLY`) during peak hours.
3. Don't grant `SUPERUSER` privileges to application roles.
4. Don't rely solely on automated backups; verify they work.
5. Don't ignore alerts for long-running transactions or deadlocks.
6. Don't change database configuration without testing in staging first.
7. Don't run heavy analytical queries on the primary writer database.
8. Don't use default PostgreSQL configurations for production workloads.
9. Don't execute Prisma migrations blindly without inspecting the generated SQL.
10. Don't allow unbounded connection growth from application servers.
11. Don't forget to configure WAL archiving for PITR.
12. Don't leave unused or orphaned tables in the database.
13. Don't perform major version upgrades without extensive testing.
14. Don't store plain text credentials in database configurations.
15. Don't disable essential logging for performance reasons.

## 8. Quality Gates
- PgBouncer successfully handles 5000+ concurrent connections in load testing.
- Backup restoration tested and verified within RTO/RPO limits.
- No queries consistently take longer than 500ms without optimization plans.

## 9. Escalation Path
- Escalate database downtime or data corruption immediately to the Tech Lead and Incident Response Team.
- Escalate unoptimized queries causing performance degradation to Database Engineers.

## 10. KPIs & Success Metrics
- Database Uptime (99.99%).
- Query latency (p95 < 100ms).
- Successful backup restoration rate (100%).
